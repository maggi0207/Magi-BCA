## 6. Implementation Dependency Order

Derived from repository evidence (not the suggested template order) — reasoning given per step:

1. **Resolve `TaskType.Npp` wiring decision (Gap 1 / Gap 7).** Every other capability (task list inclusion, UI component, CACTUS branch, PDF type, reporting index) depends on how this scaffold value is activated: `PafProcessingStrategyContext`, `TaskDeterminationService.GetAvailableTaskListAsync`, and `PafExtensions.GetCredentialingTypeRtk()` must all be extended together or the pipeline will throw (`ArgumentOutOfRangeException` is the confirmed default behavior for unhandled `TaskType` values in `PafExtensions.cs`). This must also settle whether `PafType` needs a new value (Gap 7) — evidence favors *not* needing one, following the `AddPractitionerToFacility` precedent.
2. **Begin NPP PAF entry point (136873, 136876, 136878, 136882, 136883).** This is UI-only and has no dependency on Step 1 — it only needs to route to the *existing* `PractitionerSearchPage`/`PractitionerSearchForm`. Can proceed in parallel with Step 1, but ticket 53658 explicitly states 136871 (parent epic) must be deployed before search-feature work (Step 3) begins.
3. **NPI/exception search reuse verification (53658, 127104).** Requires resolving the Repository Evidence Gap on exact existing exception-search fields (see §5) before confirming reuse actually satisfies V5 §8 — this is a verification task, not new code, per ticket intent ("no new NPI search logic").
4. **Task determination + requiredness rules (Gap 1 continuation, §5 of V5).** Once `TaskType.Npp` is wired into `TaskDeterminationService`, add the Net-New/Existing-Inactive branching logic.
5. **Task-scoped UI: Demographics, Address, Specialty (including PPI), ADD NPP to Facility card.** These extend existing components (`ManagePractitionerInformationTask`, `ManageAddressesTask`, `ManageSpecialtiesTask`) and are naturally sequenced after Step 4 establishes the task exists and is reachable.
6. **VA/PA branching + License/PSV.** Depends on Step 5 (task UI must exist to host these questions); License section visibility and requiredness are directly conditioned on VA/PA answers per V5 §15, so VA/PA must be modeled before License.
7. **Submit-time validation and routing (state-match validation, VA/PA/license-status → CPC).** Depends on Steps 5-6 being complete since `SubmitPafStrategy` validates the fully-populated task.
8. **Auto-acceptance mechanism (Gap 2).** This is the largest unknown (no existing extension point) and logically depends on Step 7's routing decision (normal vs. exception) already being computable.
9. **CVI creation for exceptions (Gap 5).** Depends on Step 8 (must know an exception was routed) and requires office-sourced CACTUS RTK values before any code can be written.
10. **CACTUS write-path extension (Gap 26/Gap 18 in tables above — new `TaskType.Npp` branches in every `Crud*Operation` class).** Can technically proceed in parallel with Steps 5-7 for the *shape* of the operations, but final field-mapping correctness depends on Demographics/Address/Specialty/License being finalized first.
11. **PDF/history template (Gap 28).** Depends on Step 10 (CACTUS data must exist to render) but is otherwise independent of CPC/CVI logic.
12. **Reporting (Gap 6).** Depends on Step 4 (task must be indexed) and Step 9 (CVI type must exist for MOR exclusion) — logically last since it aggregates completed data.
13. **Regression testing of existing Begin PAF / Add Practitioner to Facility (136882).** Must run continuously alongside every step above, not merely at the end, since ticket 136882 makes "no regression" an explicit acceptance criterion of the very first ticket in this sequence.

## 8. Executive Summary

1. **What ADD NPP can directly reuse today:** NPI-required practitioner search and its 10-digit validation (`ValidationRoutines.DoNpiValidation`), the Add New Practitioner form/modal (`AddNewPractitionerForm`/`ConfirmationWizardModal`), the generic attachment/PSV upload pipeline (`PafFile.razor`, `PafController.UploadPafAttachmentAsync`), the PAF/CACTUS audit and history mechanisms (`ICredentialingAuditLogger`, `CactusUpdater.CreatePafHistoryAsync`), and duplicate-practitioner detection (`PractitionerDuplicateCheckHelper`).

2. **What can be extended:** The PAF task framework (`TaskType`/`PafProcessingStrategyContext`/`AddTaskXStrategy`/`UpdateTaskXStrategy`) already has a reserved `Npp` value ready to be wired in; the entire Add-Practitioner-to-Facility CACTUS write pipeline (`Crud*Operation` classes) is a proven, directly analogous pattern; `ManagePractitionerInformationTask`'s conditional-requiredness mechanism and `ManageSpecialtiesTask`'s primary-required validation are structurally reusable; `CrudEntityCredentialingOperation`'s RTK-driven CVI due-date mapping and `PdfType`'s template dispatch are both proven, table-driven extension points.

3. **What appears missing:** An auto-acceptance mechanism of any kind (searched exhaustively — none exists); any VA/Active-Duty/PA concept in code; any PPI (Professional Practice Interest) concept in code; a standalone (non-Recruitment-scoped) License PAF task with facility-state-match validation; `LicenseStatus` enum values for Temporary Permit/Active Military/Active-Compact; the CACTUS RTK constant for "Facility Undefined Practitioner"/"UDP Facility Request"; and a general-purpose (non-Recruitment-hardcoded) reporting mechanism.

4. **What requires deeper repository investigation:** The exact existing no-NPI exception-search field set (to confirm it matches or must be reconciled with V5 §8); whether `LicenseStatus`'s defining file truly excludes the three missing statuses; whether "HCA Corporate" already has an audit-identity representation; and — most promisingly — whether the `NPP - Active/Inactive/Suspend` CACTUS entity-assignment status RTKs already found in `Portal.Api`'s query builders are the same statuses V5 §22 expects for Entity Assignment (this could substantially de-risk that requirement if confirmed).

5. **Which dependencies must be resolved first:** The `TaskType.Npp` wiring decision (Gap 1) and its entanglement with whether `PafType` needs a new value (Gap 7) are the single most upstream decisions — nearly every other requirement (Demographics, Address, Specialty, Facility, License, PSV, Submit, CACTUS, PDF, Reporting) attaches to how this task is activated.

6. **Which ticket appears technically ready for the next implementation step based only on evidence:** **136873** (Begin NPP PAF dashboard button) has fully captured acceptance criteria and a fully traced, unambiguous insertion point (`PafQueueSearchCriteria.razor.cs`) with no unresolved repository questions — it is the most implementation-ready ticket in the entire set. **136878** (route to existing Enforce NPI Search) is similarly ready, since its destination is fully traced. **136882** (preserve Begin PAF) is ready as a regression-verification ticket. Tickets **136876** and **136883** are partially ready pending confirmation of an existing tooltip pattern and the exact NPP authorization boundary, respectively. Every ticket beyond the entry-point epic (53658 onward) has at least one unresolved Repository Evidence Gap or missing ticket AC and is not yet ready.

7. **Which repository evidence should be brought back to Cursor:** (a) the caller of `PafQueueSearchCriteria` that supplies `CanBeginPaf`; (b) the exact field list/validation of the existing no-NPI exception search mode; (c) the `LicenseStatus` enum's defining file and full value list; (d) confirmation of whether `NPP - Active/Inactive/Suspend` CACTUS RTKs found in `Portal.Api` are the Entity Assignment statuses referenced by V5; (e) full Azure DevOps acceptance criteria for every "title only" ticket in §1, especially 131728 (RBAC), 132591 (Auto-Acceptance), 132537 (CVI), and 132600 (CACTUS sync), since these four carry the largest unresolved architectural risk; and (f) the actual CACTUS RTK reference values for "Facility Undefined Practitioner" credentialing type and its two statuses, which cannot be sourced from this repository at all.
