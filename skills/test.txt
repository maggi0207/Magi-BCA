**A. Entry Points**

- The queue’s **Begin NPP PAF** button navigates to `/Practitioner/Search/Npp`. It is displayed only when `IsMspOnlyUser` is true.
- `PractitionerSearchPage` detects that route and redirects users who are not in the MSP role to the root page.
- The PAF Action radio is populated from `GetAvailableTaskList`; `TaskDeterminationService` adds NPP only when the MSP flag is true.
- The NPP action is ultimately added through `PUT api/Paf/AddTaskToPaf?task=Npp`.

**B. UI MSP Gates**

The queue button is conditional:

> `@if (IsMspOnlyUser)`

`IsMspOnlyUser()` uses the exact MSP role:

> `return _currentUser?.IsInRole(nameof(HcoApplicationRole.Msp)) ?? false;`

The NPP route also redirects non-MSP users:

> `if (_isNppEntry && !_currentUser.IsInRole(nameof(HcoApplicationRole.Msp))) { NavigationManager.NavigateTo(PageUri.RootUri); return; }`

The available-task API overwrites the client-supplied MSP mode from the authenticated principal and fails closed for listing if principal resolution fails:

> `listParameters.IsMspUserMode = currentUser.IsInRole(nameof(HcoApplicationRole.Msp));`

> `catch (Exception ex) { listParameters.IsMspUserMode = false; ... }`

The task determination service then adds `TaskType.Npp` only for that server-derived mode.

**C. API MSP Gates**

The API controllers have `[Authorize]`, which requires authentication, not the MSP role. There is no MSP-specific gate in these action methods:

- `PafController.AddTaskToPafAsync`
- `PafController.CreateNewPafAsync`
- `PafController.UpdateTaskAndSavePafAsync`
- `PafController.SubmitPafAsync`
- `TaskController.GetAvailableFacilityListAsync`

`CreateAddTaskStrategy` maps NPP directly to the shared Add-Practitioner strategy:

> `TaskType.Npp => new AddTaskAddPractitionerToFacilityStrategy(this)`

That strategy has a PSG-specific branch which adds a `PerfTask` for eligible practitioners. Thus, PSG cannot use the normal NPP entry point or see NPP in the server-derived list, but an authenticated PSG (or other authenticated caller) can directly call `AddTaskToPaf?task=Npp`; the server will build the NPP task. Direct `UpdateTaskAndSavePaf?task=Npp` likewise has no MSP role check.

**D. Submit Path Auth**

The `SubmitPaf` endpoint delegates directly to `SubmitPafStrategy`. For MSP users, NPP receives its NPP submit handling. But the role dispatch is not NPP-exclusive:

- CPC users enter `ProcessSubmitForCpcAsync`, the review/decision flow.
- Recruiter users enter `ProcessSubmitForRecruitmentAsync` without checking that `TaskSelected` is Recruitment. That branch can reach success and set `SubmittedByRecruiter` for an NPP form.

Unknown/PSG users generally leave the result at its initial `Failure`, so that case fails closed in effect, but returns HTTP 200 with a failure result. The recruiter path is a clear MSP-only submit gap; CPC review/accept appears to be the existing review workflow, not initial MSP submission.

**E. Unauthorized UX / Fail-Closed**

- Begin NPP is hidden for non-MSP; direct NPP route access redirects to root. No explicit unauthorized message is shown.
- A generic failed submit displays **“PAF Submission Failed”** and usually the fallback **“Unexpected error. Please try again.”**
- The task-list endpoint logs and hides NPP if it cannot resolve the current user. That fail-closed behavior is limited to task listing.
- Direct API task-add/update paths lack the MSP gate; submit handling can dispatch recruiters to a successful non-MSP branch.

**F. Submitter Audit**

There is server-side timestamp and user audit. On successful MSP submission, `SetSubmitInfoAsync` sets:

> `formData.SubmittedDate = DateTime.UtcNow;`

The strategy’s base save path calls `SetLastUpdatedInfo(StrategyContext)`, which sets `LastUpdatedBy` from the current authenticated user’s username. Status history copies `LastUpdatedBy` into `UpdatedByName` and writes `UpdatedOn = DateTime.UtcNow`.

Caveat: `SetSubmitInfoAsync` only fills `SubmitterName` from the authenticated principal when the field is blank; a nonblank value supplied in the form is retained. The history audit identity is server-derived, but the display submitter name is not always authoritative.
