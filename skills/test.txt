**A. Existing Report Timer Pattern**

`RecruitmentReportGeneration.cs` schedules the monthly report with a six-field Azure Functions NCRONTAB expression:

```csharp
[TimerTrigger("0 0 8 1 * *", UseMonitor = false)]
```

That is 08:00 on the first day of each month. The ticket specifies the first of the month but not a run time or time zone, so those should be confirmed rather than assumed.

The existing monthly query calculates its date range in SQL:

```sql
AND CONVERT(DATE, IndexedSubmittedDate) >= DATEADD(MONTH, DATEDIFF(MONTH, 0, GETDATE()) - 1, 0)
AND CONVERT(DATE, IndexedSubmittedDate) < EOMONTH(GETDATE(), -1)
```

With `CONVERT(DATE, ...)`, that exclusive upper bound excludes the final calendar date of the previous month. It is not a correct template for the requested full-month period.

The Recruitment report currently hardcodes its recipient:

```csharp
var fromEmail = "credentialing@parallon.com";
```

Other report functions use `BatchRrfcGenerationSettings.ReportToEmail`, bound from the `BatchRrfcReportToEmail` configuration key. The notification settings also expose `FromEmail` and `ToEmailOverride`; `Notifications.ResolveToEmailValue` uses the override when configured.

Email delivery in this report follows the existing Service Bus notification path: the report queues a `SendEmailRequest`, and `Notifications` sends it through `NotificationService`/Raven. `GraphMailService` exists, but it takes an email-address string for recipients; no directory-group lookup or PARA DL-name resolution was found. The strings “PARA.DL American SSC CPC FO MGMT” and “PARA Credential Reporting” were not found in the repository. **There is email infrastructure, but no demonstrated DL-name-to-address mechanism.** I have not supplied or inferred addresses.

**C. How to Count Add NPP Received**

The PAF model has `IndexedTaskSelected`, `IndexedPafStatus`, `IndexedCreatedOn`, and `IndexedSubmittedDate`. `SetIndexedProperties` maps `IndexedCreatedOn = _formData.CreatedOn` and `IndexedTaskSelected = _formData.TaskSelected`.

The existing Recruitment monthly query counts by status/task and `IndexedSubmittedDate`, not creation date:

```sql
COUNT(Id) AS PafCount
...
WHERE IndexedPafStatus = 15
    AND IndexedTaskSelected = 13
    AND CONVERT(DATE, IndexedSubmittedDate) >= ...
    AND CONVERT(DATE, IndexedSubmittedDate) < ...
```

In the current enums, task value `13` is `TaskType.Npp`, and status value `15` is `PafStatus.SubmittedByRecruiter`. That numeric query is therefore not a safe semantic template for an “Add NPP received” metric, despite the Recruitment report’s name. The ticket needs to confirm whether “received” means created (`IndexedCreatedOn`) or submitted (`IndexedSubmittedDate`).

**D. How to Count Routed to CPC**

For the regular MSP submit path, `SubmitPafStrategy.ProcessSubmitForMspAsync` does:

```csharp
FormData.SetStatus(FormData.Status == PafStatus.SavedByMsp ? PafStatus.SubmittedByMsp : PafStatus.ResubmittedByMsp, null);
CurrentPaf.IndexedSubmittedToCpcCount += 1;
```

The NPP auto-accept path also sets `SubmittedByMsp`, increments `IndexedSubmittedToCpcCount`, and queues processing:

```csharp
FormData.SetStatus(PafStatus.SubmittedByMsp, null);
CurrentPaf.IndexedSubmittedToCpcCount += 1;
_shouldQueuePafForProcessing = true;
FormData.SetAcceptedByCpcUserInfo(StrategyContext);
```

The status enum comments describe `SubmittedByMsp` and `ResubmittedByMsp` as synonyms for pending CPC review. However, the NPP auto-accept path uses the same status and counter. **STOP:** the repository does not establish a single field that distinguishes “routed to CPC” from auto-accepted NPP. Candidate interpretations are the submit counter, submitted/review statuses, or CPC queue state; each needs product confirmation, particularly because the status/counter are shared with auto-accept.

**E. Email Body Pattern**

The Recruitment report builds an inline HTML body with tables using `TemplatedNotificationRequestBuilder`; it does not attach a CSV or Excel file. For very large bodies it can move the body to Blob Storage and queue a blob reference.

It calls report generation after querying regardless of whether results are empty. That supports sending an all-zero report, though the NPP implementation must explicitly render zero-valued metrics rather than rely on empty grouped query rows.

**G. Gaps vs. 132688**

- No repository implementation resolves the two requested DL names to email addresses.
- “Received” does not identify whether to count by created or submitted date.
- The existing monthly query excludes the previous month’s last day.
- “Routed to CPC” has no distinct NPP marker in the inspected submit paths; auto-accept shares status and counter updates.
- The report’s time zone and execution time are not specified beyond “1st of each month.”
- Percentage precision and zero-denominator behavior are specified by the ticket, but no NPP report implementation or tests exist.

**H. Smallest Implement Shot or STOP**

Do not reuse the Recruitment query’s numeric filters or date bounds.
