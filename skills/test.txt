**PafFile path and comparison**
`PafFile.razor` uses Ant Upload with its helper URL, bearer headers, metadata, and callbacks. Its code-behind sets:

```csharp
_uploadHeaders["Authorization"] = _authenticationHeaderValue.ToString();
_currentPafId = StateContainer.PafState.FormId;
```

Before upload it validates that FormId, FormType, and TaskId are non-null, then builds:

```csharp
var uploadDetail = new PafAttachmentUpload()
{
    FormType = FormType!.Value,
    TaskId = TaskId!.Value,
    PractitionerActionFormId = _currentPafId!.Value
};
```

It does **not** set `FacilityKey`. On a failed upload response, `PafFile.razor.cs` sets `_showFileUploadErrorMessage = true`; `PafFile.razor` renders “The upload of the file you selected failed. Please try again.” On success, the component creates an `AttachedFile`, sets its own `Attachment` to the returned ID and filename, and renders the filename link and Remove button.

The OffCycle host uses this markup:

```razor
<InputHca @bind-Value="@context.Mss019RequestFileAttachmentUrl" Type="hidden" />
<PafFile Attachment="@context.Mss019RequestFile"
         FormType="PractitionerActionFormAttachmentType.Mss19LoaForm"
         TaskId="@StateContainer.PafState.OffCyclePsvTask.TaskId"
         OnAfterUpload="(e) => HandleAfterUpload(e, PractitionerActionFormAttachmentType.Mss19LoaForm)"
         OnAfterRemove="(e) => HandleAfterRemove(e, PractitionerActionFormAttachmentType.Mss19LoaForm)" />
```

MSS-18 and Delegate use the same attachment, task ID, upload callback, and remove callback pattern. Those hosts also omit FormId and FacilityKey parameters because PafFile derives FormId from PafState and does not expose a FacilityKey parameter.

**NPP values and likely blocker**
NPP currently passes:

```razor
Attachment="@context.LicensePsvAttachment"
FormType="PractitionerActionFormAttachmentType.Other"
TaskId="@StateContainer.PafState.NppTask.TaskId"
```

The same wiring is used for Sanctions and NPI. PafFile internally gets FormId from `StateContainer.PafState.FormId`; FacilityKey is omitted and therefore null. The PAF shell saves/loads the PAF before entering its task view. Also, PafFile’s null-state guard runs before sending the upload, so the reported *server upload failure* is not caused by a null TaskId or null FormId. The attachment table allows null FormId and FacilityKey.

The concerning shared API/schema mismatch is that the only attachment DDL in the repository declares `[Version] INT NOT NULL` with no default, while `PractitionerActionFormAttachment` has no `Version` property. `UploadPafAttachmentAsync` builds that entity without Version, and `CreatePafAttachmentAsync` inserts it directly via `conn.InsertAsync(pafAttachment)`. If the live table follows this DDL and has no out-of-band default, the insert fails for **every** PafFile host, not just NPP. The source has no later migration/default to resolve this. I cannot confirm the live database’s actual default constraint or see the authenticated upload response from this session, so this is a likely shared failure rather than a proven live response. Because fixing it requires an API/schema change outside NPP’s upload contract, I stopped rather than adding a client workaround.
