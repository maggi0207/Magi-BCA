**A. Call Chain: Submit to Provider Write**

The submit strategy queues accepted PAFs with `_pafProcessingService.QueuePafForProcessingAsync(FormData.FormId)` in `SubmitPafStrategy.cs:113`. The service’s Development-mode branch returns before it sends a message:

> `if (_settings.IsDevMode) ... _logger.LogWarning("... in dev mode skipping processing queue"); return;`

Otherwise it sends through Service Bus. The `PafProcessorFunction.cs:39` listens on `paf-processing` and calls `CactusUpdater.UpdateCactusFromPafAsync`. That method loads the PAF, then `InternalUpdateCactusFromPafAsync` chooses manual processing, `UpdateFromNewAsync` when `Practitioner.IsNew`, or `UpdateFromExistingAsync` otherwise. The new and existing paths invoke `CrudPractitionerOperation` under different conditions.

**STOP for Current Local UAT:** the PAF API launch profile sets `ASPNETCORE_ENVIRONMENT` to `Development`, and startup derives `IsDevMode` from `Environment.IsDevelopment()`. Therefore, the reported UAT submit cannot reach the processor/provider operation in that local run: the queue message is skipped. This is a queue gate, not a missing NPP arm. I did not infer or propose a synchronous product path.

**B. Exist Check**

`CrudPractitionerOperation` branches on the loaded PAF practitioner’s `IsNew` flag:

> `if (practitioner.IsNew) { if (!await PractitionerValidations.IsUniqueAsync(practitioner)) ThrowPafProcessingError("New provider already exist"); return await SavePractitionerAsync(); } return await UpdatePractitionerAsync();`

The new-practitioner duplicate check queries `VISUALCACTUS.PROVIDERS` by SSN and then NPI. It does not look up a matching record by Provider_K; the existing-practitioner path uses the PAF practitioner’s `Key`.

**C. Create Path**

For a net-new practitioner, `UpdateFromNewAsync` invokes `CrudPractitionerOperation`, which generates a Provider key and executes an `INSERT INTO VISUALCACTUS.PROVIDERS`. No `TaskType.Npp` exclusion is present in this path. Thus, when a queued NPP PAF has `Practitioner.IsNew == true`, the same create path used for other net-new PAFs is selected.

**D. Preserve/Skip Existing**

The existing path retrieves the provider by key and deep-copies it, but does **not** preserve all demographic fields. It subsequently updates and persists a changed record. First name, last name, suffix, display degrees, and NPI are commented out in the update method; however SSN, date of birth, sex, category, contact email, and cell phone are assigned from the PAF demographic task before `UpdateAsync`.

That conflicts with 132604’s “no Provider demographic fields updated” acceptance criterion when this operation runs. It is not an unconditional “existing provider unchanged” path.

**E. PAF to PROVIDERS Mapping**

The ticket’s `PROVIDERS.*` names are destination columns. The actual source values are from `PafDataContext.Paf.PractitionerDemographicTask` (`prac`), not `NppTask`:

- `FIRSTNAME` ← `prac.FirstName`
- `LASTNAME` ← `prac.LastName`
- `SUFFIX` ← `prac.Suffix`
- `DISPLAYDEGREES` and `DISPLAYDEGREES_SHORT` ← `prac.Degrees`
- `NPI` ← `prac.Npi`
- `CATEGORY_RTK` ← `prac.GetPractitionerCategoryRtk()`, which maps `prac.Category`

The insert also derives `LONGNAME` and `SORTNAME` from the demographic task.

**F. NPP-Specific Gap vs Add-Practitioner**

**No missing NPP processor arm** was found: create/existing dispatch is based on `Practitioner.IsNew`, with no NPP-specific exclusion around `CrudPractitionerOperation`.

**Yes, a behavior gap exists for 132604:** the shared existing-provider update changes several provider fields instead of preserving all demographics. The current local Development queue skip additionally prevents this operation from being reached in the reported UAT run.

Duplicate-match failures are thrown as `PafProcessingException`, caught and logged by `CactusUpdater`, recorded in PAF history, and leave the update unsuccessful; they do not continue into downstream provider/CVI processing.
