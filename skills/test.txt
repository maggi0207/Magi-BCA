**A. Call Chain**

- For a net-new practitioner, `CactusUpdater.UpdateFromNewAsync` creates the practitioner and then unconditionally calls `CrudPractitionerSpecialtiesOperation` under `// Specialties`. The operation’s `InternalExecuteAsync` routes `Practitioner.IsNew` to `SavePractitionerSpecialtiesAsync`.
- For Add-Practitioner on an existing practitioner, the updater calls the specialty operation only when `SpecialtyTask.Status == Complete`; that operation routes to `UpdatePractitionerSpecialtiesAsync`.
- The completed NPP branch calls `CrudPractitionerLicensesOperation` and then creates CVI records; it does **not** call the specialty operation. `CrudPractitionerOperation` also returns the existing practitioner key without updating the provider row for `TaskType.Npp`.

Evidence: `CactusUpdater.cs`, `CrudPractitionerSpecialtiesOperation.cs`, `CrudPractitionerOperation.cs`

**B. Primary Create**

For new practitioners, the existing operation creates a primary row from `Paf.SpecialtyTask.Primary`:

> `SavePractitionerSpecialtyAsync(providerSpecialties.Primary.Key, CommonCactusRtks.PrimaryProviderSpecialtyTypeRtk)`

The constant is present: `PrimaryProviderSpecialtyTypeRtk = "PRSPTYPRIM"`. The insert sets `Active = true`, but sets `SpecialtyStatusRtk = CommonCactusRtks.NoneRtk`. The code uses the `Primary` field; it does not promote an arbitrary “first specialty selected” itself.

The specialty operation reads `Paf.SpecialtyTask`: `Primary`, `Secondary`, `AlternateSpecialties`, and, through its reconciliation path, the specialty keys and types derived from that task. `NppTask` has no specialty fields. Its `ProfessionalPracticeInterest`-like value is not present there; the `ProfessionalPracticeInterest` property belongs to the separate `SpecialtyTask`.
