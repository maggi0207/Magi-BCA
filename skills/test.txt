**A. Recruitment/PSG Exception**

In `PractitionerSearchForm.razor.cs`, flexible mode is exactly:

```csharp
private bool IsFlexiblePafUser() => _isRecruitmentUser || _isPsgUser;
```

The exception form shows Reason, SSN, First Name, Last Name, DOB, and Practitioner Email; it omits NPI. The current reason list has one entry: `"Practitioner does not have NPI"`.

```csharp
var hasAtLeastOneAdditionalCriterion =
    !string.IsNullOrWhiteSpace(_model.PractitionerFirstName) ||
    _model.DateOfBirth.HasValue ||
    _model.HasAnySsn() ||
    !string.IsNullOrWhiteSpace(_model.PractitionerEmail);

return !string.IsNullOrWhiteSpace(_selectedReason)
    && !string.IsNullOrWhiteSpace(_model.PractitionerLastName)
    && hasAtLeastOneAdditionalCriterion;
```

For flexible users, Last Name is required and must be at least two trimmed characters; First Name is optional. The UI also requires the selected Reason and at least one of First Name, DOB, SSN, or Email. The exception request logs the reason, names, DOB, and whether SSN/email were supplied, but does not send the reason in the search parameters.

`ShowNoNpiOption` is separate: in `AddNewPractitionerForm.razor`, it controls an add-new wizard choice between “Enter NPI” and “No NPI,” with its own two reasons (“Provider currently in training program” and “Unknown”). It is not the exception-search Reason control.

**B. MSP Exception**

The non-flexible exception UI has NPI, SSN, First Name, and Last Name. It does not show Reason, DOB, or Email. Its button rule is:

```csharp
return (_model.HasAnyNpi() || _model.HasAnySsn() ||
    (!string.IsNullOrWhiteSpace(_model.PractitionerFirstName) && !string.IsNullOrWhiteSpace(_model.PractitionerLastName)));
```

Switching to exception mode clears NPI, so MSP exception search effectively requires SSN or both First and Last Name. Existing MSP validators also allow SSN to bypass the name requirements.

**C. `/Npp` Behavior Today**

`PractitionerSearchPage.razor.cs` identifies the NPP route and redirects users without the MSP role:

```csharp
if (_isNppEntry && !_currentUser.IsInRole(nameof(HcoApplicationRole.Msp)))
{
    NavigationManager.NavigateTo(PageUri.RootUri);
    return;
}
```

`PractitionerSearchPage.razor` passes `ForceNpiSearchMode="@_isNppEntry"`. In `PractitionerSearchForm.razor.cs`, that flag only prevents the initial MSP auto-switch:

```csharp
if (!_isRecruitmentUser && !_isPsgUser && !ForceNpiSearchMode)
{
    SwitchToExceptionSearch();
}
```

It does not disable the always-rendered “No NPI available?” link or block `SwitchToExceptionSearch`. Also, `SwitchToNpiSearch` calls browser `history.back` for non-flexible users rather than changing the form mode. Thus `/Npp` starts in NPI mode, but the shared exception toggle remains available and Cancel is not guaranteed to return to NPI mode.

**D. Shared API vs. 131785 License Match**

`PractitionerSearchForm.razor.cs` builds the existing exception request as:

```csharp
searchParams.SearchType = PractitionerSearchType.Recruitment;
searchParams.LastName = _model.PractitionerLastName;
searchParams.FirstName = _model.PractitionerFirstName;
searchParams.DateOfBirth = _model.DateOfBirth;
searchParams.EmailAddress = _model.PractitionerEmail;
searchParams.Ssn = ssnRawValue;
```

The form then calls `OnSearchCallback`; `PractitionerSearchTable.razor.cs` calls `SearchExistingPractitionersAsync`. The shared `PractitionerSearchParameters.cs` has no State, license number, or exception-reason property.

`PractitionerSearchType.Recruitment` dispatches to `RecruitmentMatchSearchPagedQueryBuilder` in `PractitionerRepository.cs`. Its exception branch matches LastName and any supplied FirstName, SSN, Email, or DOB using `AND` criteria. It has no State/license-number match.

Practitioner-license APIs do exist, but the inspected contracts do not provide that reverse lookup. `PractitionerLicenseSearchParameters.cs` accepts PractitionerKey, DelegateEmail, Name, and paging. `PractitionerLicenseController.cs` exposes state-license retrieval by practitioner key and searches for expired, unverified, or verified license items. The state-license repository query filters by practitioner key and a specific license RTK; it is not a state-plus-license-number-to-practitioner search. I found no existing `PROVIDERLICENSES` search usable for the 131785 exception match.

**E. Safe NPP-Only Reuse Plan**

Reuse the shared search UI and transport mechanics, but keep NPP out of `IsFlexiblePafUser`:

- `PractitionerSearchPage._isNppEntry`, `PractitionerSearchPage.OnInitializedAsync`
- `PractitionerSearchForm.ForceNpiSearchMode`, `SwitchToExceptionSearch`, `SwitchToNpiSearch`, `IsExceptionButtonEnabled`, `OnFinish`
- `PractitionerSearchTable.ExecuteSearch`, `LoadPractitionersAsync`
- `PractitionerClient.SearchExistingPractitionersAsync`
- `PractitionerRepository.SearchPractitionersAsync` as the dispatch point for a dedicated NPP search path
- Existing NPP modal hooks: `PractitionerSearchTable.IsNppRequest`, `ConfirmationWizardModal.IsNppRequest`, `AddNewPractitionerForm.IsNppRequest`

Add NPP-specific exception state/validation and an NPP-isolated search contract/query path rather than changing Recruitment/PSG flexibility or reusing `PractitionerSearchType.Recruitment`.

**F. Do Not Reuse / Stop Items**

- Do not make NPP an `IsFlexiblePafUser`; that property deliberately means Recruitment or PSG.
- Do not use the current `PractitionerSearchType.Recruitment` query as the final NPP search path; it is not NPP-isolated and has no license criteria.
- Do not treat `ShowNoNpiOption` or the add-new wizard’s NPI reasons as the NPP exception-search controls.
- Stop before implementing the license “VC” match until the product meaning of “VC,” supported VisualCACTUS lookup path, matching/normalization rules, and multiple/no-match behavior are confirmed. No provider-license search API was inferred.
- Stop before implementing audit until the required durable audit event, identity/timestamp, retained criteria, and handling of sensitive values are specified. The current exception path emits a UI `Logger.LogInformation`; it does not pass Reason in its search request or queue the audit event used by the separate affiliation-verification path.
