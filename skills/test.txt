**A. Specialty Work target**

```razor

```

Its Work button calls:

```razor
HandleRequestEditAsync(EditSource.Edit, TaskType.ManageSpecialities)
```

`HandleRequestEditAsync` routes that type to `PractitionerPafViewState.ManageSpecialties`.

**B. Primary / Secondary / Alternate and save**

The component’s `_specialtyTargets` contains Primary and Secondary. Alternate is rendered in a separate card. All three are shown today; no NPP visibility condition exists.

```csharp
private readonly ICollection<SpecialtyTarget> _specialtyTargets = new List<SpecialtyTarget>
{
    SpecialtyTarget.Primary,
    SpecialtyTarget.Secondary
```

It then reports `TaskStatus.Complete` and saves Primary, Secondary, and Alternate specialties.

**C. Load source and active mapping**

`ManageSpecialtiesTask.OnInitialized()` loads the PAF specialty task and existing practitioner specialties:

```csharp
_specialtyTask = StateContainer.PafState.SpecialtyTask;
_existingSpecialties = StateContainer.PafState.Practitioner.Specialties;
```

`InitializeFromPractitioner()` seeds the task’s Primary/Secondary/Alternate values from `Practitioner.Specialties`.

Cactus maps the specialty RTK to `PractitionerSpecialty.Key`:

```sql
SELECT DISTINCT s.SPECIALTY_RTK AS [Key],
    RTRIM(r.[DESCRIPTION]) AS [Name],
    RTRIM(r2.[DESCRIPTION]) AS [Status],
    RTRIM(r3.[DESCRIPTION]) AS [Type]
...
WHERE s.ACTIVE = 1
  AND s.PROVIDER_K = @practitionerKey
```

Thus active specialties are included in the practitioner collection, but the raw `PROVIDERSPECIALTIES_ACTIVE` value is not returned as a model property. `PractitionerSpecialty.Status` maps the description for `SPECIALTYSTATUS_RTK`, not the row’s `ACTIVE` bit.

**D. Selector and current lock**

The “Select Specialty” button uses `Disabled="IsDisabled(target)"`. For a selected existing specialty, `IsDisabled` checks whether it is present in `_existingSpecialties`:

```csharp
return ((target != SpecialtyTarget.Alternate) &&
        (GetSpecialty(target + 1) != null)) ||
       (_existingSpecialties?.Contains(GetSpecialty(target)) ?? false);
```

The modal is `SelectSpecialtyModal`; it loads choices using `Cactus.PractitionerSpecialties.GetAllSpecialtiesAsync()`.

This means a selected Primary found in the active-filtered Cactus practitioner-specialty list is already disabled from being cleared. The form does not expose an explicit active boolean or an NPP-specific lock. No tooltip is shown for this disabled state.

**E. Professional practice interest**

No professional-practice-interest/comment field exists in the Manage Specialties form or `SpecialtyTask`. The `SpecialtyTask` model contains Primary, Secondary, and Alternate specialties only. No PPI table/API is established here.

**F. Current requiredness**

Primary has a Required badge in the form and `SaveSpecialties()` blocks saving without it. Net-new vs existing influences whether the task itself is required:

```csharp
practitionerSpecialtyTask.IsRequired = practitioner.IsNew;
```

There is no existing Primary-OR-interest rule or NPP-specific requiredness. Interest-only save would fail the Primary check and there is no interest field in the save event/model.

**G. Tooltip pattern**

No tooltip exists in `ManageSpecialtiesTask` for the disabled selected Primary. Other PAF task components do use Ant Design `Tooltip`, but this task has no current tooltip or privilege message. The active lock can reuse the existing disabled-selection pattern when the specialty is in `_existingSpecialties`; the requested exact hover text would still need to be added to this form.

**H. NPP isolation**

`ManageSpecialtiesTask` has no `IsNppPaf` parameter and does not read `TaskSelected`. The parent currently renders it without an NPP discriminator:


The parent can pass the same discriminator used by the other task forms:

```razor
IsNppPaf="@(StateContainer.PafState.TaskSelected == TaskType.Npp)"
```
