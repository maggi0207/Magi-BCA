## 3. A–N answers (short quotes)

**A. Task list and Save Facilities path**

`PafTaskSelection.LoadAvailableTasks()` uses practitioner status:

```csharp
var isNewPractitioner = StateContainer.PafState.Practitioner is {IsNew: true};

Mode = isNewPractitioner
    ? TaskAllowedListMode.NewPractitioner
    : TaskAllowedListMode.ExistingPractitioner
```

The server adds NPP for MSP users:

```csharp
if (listParameters.IsMspUserMode)
{
    list.Add(new()
    {
        Name = "ADD NPP to Facility",
        Type = TaskType.Npp
    });
}
```

After facility selection, `PafFormComponent` calls:

```csharp
result = await PafClient.AddTaskToPafAsync(eventArgs.PafType.Value, PafData);
```

The resulting PAF task cards are not dynamically enumerated; they are hardcoded component blocks in `PafFormComponent.razor`.

**D. Required versus optional**

The task model stores the decision here:

```csharp
public virtual bool IsRequired { get; set; }
```

The new/existing signal is already present:

```csharp
TaskAllowedListMode.NewPractitioner
TaskAllowedListMode.ExistingPractitioner
```

and the UI derives it from:

```csharp
StateContainer.PafState.Practitioner is { IsNew: true }
```

`IsSubmittable()` evaluates required tasks differently:

```csharp
if (task.IsRequired)
    return task.Status != TaskStatus.Complete;
else
    return task.Status != TaskStatus.New && task.Status != TaskStatus.Complete;
```

The current NPP add strategy sets the facility task required:

```csharp
FormData.AddPractitionerToFacilitiesTask = new AddPractitionerToFacilitiesTask()
{
    IsRequired = true
};
```

However, it reuses the standard Add Practitioner strategy and does not visibly establish the NPP-specific required/optional matrix. The NPP card itself is also absent.

**E. Task status and refresh**

Status is stored on every task:

```csharp
public virtual TaskStatus Status { get; set; } = TaskStatus.New;
```

Allowed values are:

```csharp
New,
Invalid,
Complete
```

After a task saves, `PafFormComponent.SavePafAsync()` reloads the server result:

```csharp
PafData = result.PafFormData;
pafState.LoadFrom(PafData);
StateHasChanged();
```

This is the existing completion/incompletion refresh pattern and is reusable for 132264. The missing NPP Work/update path is the blocker.

**F. Review & Submit**

For MSP, `ShowReviewAndSubmit()` checks:

else if (PafData.IsSubmittable())

`IsSubmittable()` checks all instantiated tasks and requires every required task to be complete:

This gate is reusable in principle. However, because no NPP task property/card is currently present, NPP completion is not included. Also, `GetCredentialingTypeRtk()` has no NPP case:

That is a downstream 132267 blocker if NPP submission reaches that processor path.

**I. MSP / ADD NPP access**

The server computes MSP access from the authenticated principal:

```csharp
listParameters.IsMspUserMode =
    currentUser.IsInRole(nameof(HcoApplicationRole.Msp));
```

It does not trust a client-supplied role flag. NPP task selection is then guarded by:

```csharp
if (listParameters.IsMspUserMode)
```

This reuses the existing MSP role check and does not introduce a new policy. The client currently sends PSG/recruitment flags, while the server computes MSP status.
