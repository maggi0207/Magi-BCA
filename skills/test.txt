**A. Skip Condition**

`PafProcessingService.QueuePafForProcessingAsync` skips publishing when:

```csharp
if (_settings.IsDevMode)
{
    ...
    _logger.LogWarning("... in dev mode skipping processing queue");
    return;
}
```

`Paf.Api/Startup.cs` sets that value with `settings.IsDevMode = Environment.IsDevelopment();`. The PAF API launch profile sets `ASPNETCORE_ENVIRONMENT` to `Development`, so the skip is expected. There is no `IsDevMode` appsettings switch.

**B. Configuration Keys**

The PAF API gets its Service Bus sender connection from `HcoServiceBus`. Its Development appsettings contains that key, but it cannot override the Development-mode skip.

The PAF Processor function trigger is configured as `[ServiceBusTrigger("paf-processing", Connection = "HcoServiceBus")]`. Processor startup separately reads `AzureWebJobsHcoServiceBus` for its own Service Bus service.

For database connections, processor startup reads `ConnectionStrings:CactusDb` for VisualCACTUS and `ConnectionStrings:PafDb` for the PAF database. The processor’s checked-in VS Code tasks provide a build task, but no run task; no processor `local.settings.json` is present in the repository. The test Development settings show `PafDb` using LocalDB; do not assume the processor’s active `CactusDb` target is local. The PAF API Development config contains credential literals; I’m not reproducing them here. Treat those values as sensitive and handle/rotate them according to your team’s policy.

**C. Local CVI UAT Path**

- Run PAF API with a non-Development `ASPNETCORE_ENVIRONMENT`.
- Supply an approved nonproduction `HcoServiceBus` connection for the API sender.
- Start PAF Processor locally with Azure Functions Core Tools (`func host start`) and its required local settings.
- Configure the function trigger’s `HcoServiceBus` and processor sender’s `AzureWebJobsHcoServiceBus`.
- Configure `ConnectionStrings:CactusDb` and `ConnectionStrings:PafDb` for the intended UAT targets.
- Confirm the Service Bus and VisualCACTUS targets before submitting: this path publishes a real queue message and can write to the configured VisualCACTUS database.

No general synchronous product processing path was found. The only direct `CactusUpdater.UpdateCactusFromPafAsync` call found is in a processor integration test, not a local operational API.
