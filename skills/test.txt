I inspected `PageUri.cs`, `PractitionerSearchPage.razor(.cs)`, and `PractitionerSearchForm.razor(.cs)` as instructed. Finding:

- **Begin PAF and "Enforce NPI Search" are the same URL and the same component** (`/Practitioner/Search` → `PractitionerSearchForm`), not two different screens.
- `PractitionerSearchForm.OnInitializedAsync()` decides the search mode **purely by role**:
  ```csharp
  _isRecruitmentUser = currentUser.IsRecruitmentUser();
  _isPsgUser = currentUser.IsPsgUser();
  if (!_isRecruitmentUser && !_isPsgUser)
      SwitchToExceptionSearch();   // this IS today's "Begin PAF" behavior for MSP
  ```
  Only Recruitment/PSG users default to `SearchMode.NpiSearch` (the NPI-required, "No NPI available? Search without NPI" screen that matches "Enforce NPI Search"). A plain MSP user is hard-coded into `ExceptionSearch` mode immediately, which renders the free-form NPI/SSN/Name search — i.e., today's ordinary Begin PAF screen.
- Therefore, simply calling `NavigationManager.NavigateTo(PageUri.PractitionerSearchUri)` for "Begin NPP PAF" (the same call Begin PAF already makes) **would not launch Enforce NPI Search for an MSP user** — it would show them the identical screen Begin PAF already shows, because mode selection has no URL/query signal, only a role check.
- Making "Begin NPP PAF" actually reach NPI-required mode would require introducing a new signal (query parameter, session/state flag, or altering the existing role check) into `PractitionerSearchForm`/`PractitionerSearchPage` — this is new search-mode-selection logic, explicitly out of scope ("no new search," "wire click only," and the instruction to STOP if the two screens can't be safely distinguished by a click-only change).
