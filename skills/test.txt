**A. Call Chain for Image Attachment**

`PafProcessorFunction.RunAsync` receives the `paf-processing` Service Bus message and calls `CactusUpdater.UpdateCactusFromPafAsync`. The updater dispatches on `Practitioner.IsNew` to `UpdateFromNewAsync` or `UpdateFromExistingAsync`; neither dispatch has an NPP-specific image branch.

- **New provider:** `UpdateFromNewAsync` inserts through `CrudPractitionerOperation`, then processes specialties/CVIs, licenses and addresses, and later PERF/delegate authorization. It does not call the provider PAF-image helper.
- **Existing provider:** `UpdateFromExistingAsync` runs applicable task operations, then calls `UploadPafImageToProviderAsync` only when `shouldAttachPafImageToProvider` is true. That flag is set for `TaskType.ManagePersonalInfo`, not NPP. The helper calls `CrudImagesOperation` with `ParentFileK = ImageParentFileKValues.Provider` and queues that image for PAF PDF generation.

**B. NPI-Specific Path or Generic**

There is **no NPI-specific image path**, and no `TaskType.Npp` image-attach branch was found. The reusable generic helper is `UploadPafImageToProviderAsync`; it stores the provider’s PAF image, not the NPP NPI PSV attachment.

`CrudImagesOperation` accepts `FileName`, `ImageTypeRtk`, `ImageDescription`, `Notes`, and `ImageContents`. If no type is supplied, it defaults to `"D2MQ0MQ2SX"` (“Provider Action Form”).

**C. Naming, Type, Notes Today**

The generic PAF image description is generated as:

> `"{LastName≤13}_{FirstName≤3}_PAF_{facility abbreviation}_{MMDDYY}.pdf"`

The general `CrudImagesOperation` metadata uses its default Provider Action Form type, sets source to `"NOTVER2IMG"`, and derives notes from the selected task and applicable address/delegate/personal-info changes. Other task-specific image paths provide explicit type and metadata, but none handles NPI PSV. No NPI image type RTK or `{LastName13}_{FirstName3}_NPI_MMDDYY` formatter exists in the inspected path.

**D. PAF Source of NPI File**

`NppTask` contains:

> `public PafAttachment NpiPsvAttachment { get; set; }`

and a required `NpiPsvAttachmentUrl` property. The shared `PafAttachment` model holds the attachment ID and filename. The upload API stores attachment bytes in the PAF attachment repository. However, the processor has no reference to `NppTask.NpiPsvAttachment` or code that retrieves those bytes for a provider image.

**E. NPP Gap vs 132648**

**Yes, the NPI attach behavior is missing.** A present NPP NPI attachment is not read or attached to the provider; a missing attachment also causes no NPI-specific warning, skip, or throw in the processor, because that field is not consumed there. Existing provider PAF-image attachment is a separate, Manage-Personal-Info-only path.
