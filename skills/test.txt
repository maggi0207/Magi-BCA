**A. Call Chain: Sanction Record**

After acceptance is processed, `PafProcessorFunction.RunAsync` calls `CactusUpdater.UpdateCactusFromPafAsync`. The updater dispatches to new- or existing-practitioner handling; either route can invoke `CrudPractitionerLicensesOperation`, depending on its task gates. In that operation, `SavePractitionerLicensesAsync` handles Add-Practitioner defaults when `IsAddPractitionerToFacility` is true and an Add-Practitioner task is present. It also calls `CreateOrUpdateRecruitmentLicenses` when `RecruitmentPsvTask` is present.

For the Add-Practitioner default list, the operation includes:

> `"S3PK02GTA1", // Sanction Checks`

**B. Existence Check for S3PK02GTA1**

The shared lookup is by practitioner/provider key and license RTK:

> `WHERE PROVIDER_K = @ProviderK`  
> `AND LICENSE_RTK = @LicenseTypeRtk`

The Add-Practitioner default-list path checks existing licenses and avoids inserting a duplicate. If an existing matching record is nonpersistent, it updates that record. Recruitment’s `CreateOrUpdateRecruitmentLicense` uses the same lookup, reactivates/updates a match, or inserts when no match exists.

**C. Create Path**

Sanction-check creation is **not exclusive to Recruitment**. Add-Practitioner includes it in its default checklist path; Recruitment also calls:

> `await CreateOrUpdateRecruitmentLicense("S3PK02GTA1");`

The insertion is through the existing `InsertLicenseAsync(...)` method in `CrudPractitionerLicensesOperation`; no new CRUD class is needed. There is no NPP-specific call or `TaskType.Npp` branch in the processor. Whether the Add-Practitioner defaults run for an NPP PAF depends on the existing caller and task-presence/status gates.
