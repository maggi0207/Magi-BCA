You are working on an existing multi-agent application where the Runtime Agent routes user queries to MCP tools.

CURRENT PROBLEM
===============

The Runtime Agent is currently routing most/all user queries to the same MCP tool instead of dynamically selecting the correct MCP/tool based on the user's intent.

We need to fix this using LIVE MCP metadata.

IMPORTANT:
Do NOT assume the existing MCP tool descriptions, schemas, parameters, or capabilities are correct.

You MUST perform a LIVE MCP PROBE against the configured MCP server(s) and use the actual returned MCP metadata as the source of truth.

============================================================
1. LIVE MCP PROBE
============================================================

First identify the MCP server/client configuration used by the application.

Then perform a live MCP discovery/probe and retrieve ALL available MCP information exposed by the MCP server.

Fetch, wherever supported:

- All MCP servers
- All available tools
- Tool names
- Tool descriptions
- Tool input schemas
- Required parameters
- Optional parameters
- Parameter types
- Enum values
- Nested object schemas
- Tool output/response schemas
- Resource information if relevant
- Prompts if relevant
- Any tool annotations/capability metadata
- Any domain/entity information exposed by the MCP server

Do NOT rely only on:

- Existing markdown skill files
- Hard-coded tool descriptions
- Old tool metadata
- Existing routing assumptions
- Tool names alone

The LIVE MCP probe result must be treated as the authoritative runtime capability definition.

============================================================

============================================================

After probing the MCP server, create or update the runtime MCP capability model.

The capability model must allow the Runtime Agent to determine:

"For this user query, which MCP tool is actually capable of fulfilling the request?"

For every MCP tool capture information conceptually similar to:

{

Do NOT invent values.

Derive them from the live MCP schema/description and existing implementation where appropriate.

Do NOT design the router around a single MCP tool.

Remove or avoid patterns such as:

FINAL PRINCIPLE
============================================================

The LIVE MCP server is the source of truth for available capabilities.

The Runtime Agent must work like this:

USER QUERY
    ↓
UNDERSTAND INTENT
    ↓
IDENTIFY ENTITY + OPERATION
    ↓
READ LIVE MCP CAPABILITIES
    ↓
MATCH QUERY TO CAPABILITY
    ↓
SELECT CORRECT MCP TOOL
    ↓
VALIDATE INPUT AGAINST TOOL SCHEMA
    ↓
EXECUTE MCP TOOL
    ↓
PROCESS ACTUAL MCP RESPONSE
    ↓
DYNAMIC USER RESPONSE

NEVER:

USER QUERY
    ↓
DEFAULT MCP TOOL
    ↓
FORCE RESPONSE

The objective is to fix the runtime routing architecture, not simply modify a prompt.

The final system must dynamically route different user queries to the correct MCP tool based on the actual capabilities exposed by the live MCP server.
