**A. Auto-Accept vs. CPC Call Chain**

In `SubmitPafStrategy.cs`, MSP NPP submissions choose between auto-accept and the standard MSP submit path:

```csharp
if (TaskSelected == TaskType.Npp)
{
    if (NppTask?.IsActiveDutyMilitaryOrPracticingAtVa == true &&
        NppTask.IsPhysicianAssistant == true)
        await ProcessSubmitForNppAutoAcceptAsync(result);
    else
        await ProcessSubmitForMspAsync(result);
}
```

On success, `ProcessSubmitForNppAutoAcceptAsync` calls `CompleteMspAutoAcceptedSubmitAsync`. That method sets `SubmittedByMsp`, records submit information, sets the accepted-by identity, and queues PAF processing. The other NPP submissions go through `ProcessSubmitForMspAsync` for CPC review. This shows the coded VA/practicing-at-VA Physician Assistant criterion; it does not establish whether this is the complete product definition of “unless exception.”

**B. Exception Criteria**

The exact condition is:

```csharp
pafProcessingResult.PafFormData.NppTask?.IsActiveDutyMilitaryOrPracticingAtVa == true &&
pafProcessingResult.PafFormData.NppTask.IsPhysicianAssistant == true
```

The condition enables NPP auto-accept. Other NPP submissions follow the non-auto-accepted path. I found no broader exception decision in this dispatch branch.

**C. Completed Queue Timing vs. Cactus**

The auto-accept submit method sets `SubmittedByMsp` and queues processing before Cactus runs; it does **not** set `AcceptedByCpc`. The Completed queue mapping includes `AcceptedByCpc` and `ProcessedManually`, not `SubmittedByMsp`.

The PAF processor’s `CactusUpdater.cs` commits Cactus and audit changes before setting `result.Success = true`. Its PafDataContext.UpdatePaf sets `AcceptedByCpc` only for SSP Brief Enrollment, not NPP.

**BR-003 gap:** No NPP Completed transition after successful Cactus processing was found. I found no NPP path setting Completed before Cactus success either; the current gap is that the NPP completion transition is absent.

**E. Cactus Audit User and Entity**

`CactusUpdater.cs` resolves `AcceptedByCpcUserId` to a Cactus `USER_K` using `USERS.SYSTEMINITIALS`, then passes that key to `CactusAuditContext`. For the NPP auto-accept identity, the supplied application ID/name are `HCPSU` and `HCP System User`. The requested `"HCP System User – MSP Submitter Name"` composition was not found.

The audit context sets the application name to `"HCO 2.0"`. Its `BeginSessionAsync` accepts an optional `entityKOverride`, but the inspected PAF operations call it without that override. No `"HCA Corporate"` string or explicit corporate-entity override was found. The audit library may apply other defaults; the inspected repository code does not establish them.

**BR-005: No** for the requested composed audit user string.  
**BR-006: STOP.** No explicit HCA Corporate entity identity was found; do not invent one.

**F. PDF Attachment: Provider vs. CVI**

For NPP, `CactusUpdater.cs` calls `CreateStandardCviRecordsAsync` when the NPP task is complete. That helper calls `AttachPafPdfToCredentialingAsync`, which creates the PAF image with `ParentFileK = ImageParentFileKValues.Credentialing` and the credentialing key as parent. This is the existing CVI-parent mechanism.

The provider-parent path uses `UploadPafImageToProviderAsync`, which sets `ParentFileK = ImageParentFileKValues.Provider`. In the existing-practitioner flow, it is controlled by `shouldAttachPafImageToProvider`; that flag is set for Manage Personal Info, not NPP. A separate manual-processing branch attaches to the provider for an existing practitioner.

**BR-007: No demonstrated NPP provider-PDF fallback when no CVI is created.**  
**BR-008: Partial.** NPP’s created CVI receives the PAF PDF, but the code does not condition this on the product’s “exception CVI” distinction; NPP CVI creation/attachment is the observed behavior.
