**A–N**

**A. `GetExistingStateLicense`**

Found in `CrudLicensesAndCertificationsOperation.cs`, class `CrudLicensesAndCertificationsOperation`:

```csharp
private async Task<Providerlicenses> GetExistingStateLicense(
    string state, string licenseNumber, string providerKey)
```

It queries `VISUALCACTUS.PROVIDERLICENSES`, matching `PROVIDER_K`, `LICENSENUMBER`, `STATE`, and `LICENSE_RTK = "NPDBSTATEx"`. This is a **provider-scoped duplicate check**, not a reverse search: the provider key is required.

**B. Existing caller**

It is called by the Packet Processor’s license operation when processing new state-license records:

```csharp
var existing = await GetExistingStateLicense(
    stateLicense.State, stateLicense.Number ?? "", packet.Practitioner.Key);
```

The operation is invoked from `PacketProcessor`’s `CactusUpdater`, which supplies the `CactusDbContext`. This path is for packet license writes, not practitioner search.

**C. Provider key and name join**

The returned `Providerlicenses` record contains `ProviderK`; the query selects `pl.*`. The helper does not join `PROVIDERS` or filter names.

A closest API-side name lookup pattern is `AffiliationVerificationSearchPagedQueryBuilder.cs`:

```sql
LEFT JOIN VisualCACTUS.PROVIDERS P WITH (NOLOCK)
    ON P.PROVIDER_K = ea.PROVIDER_K
```

It selects `P.LASTNAME` and `P.FIRSTNAME`. That demonstrates an existing Providers join pattern, but not a ready-made license-driven lookup.

**D. Existing practitioner search API**

No PractitionerController/repository API was found that searches practitioners by state plus license number. `SearchExistingPractitionersAsync` dispatches existing search types; `PractitionerSearchParameters` contains no State or license-number fields.

**E. Exception form and NPP isolation**

`IsFlexiblePafUser()` is Recruitment or PSG only:

```csharp
private bool IsFlexiblePafUser() => _isRecruitmentUser || _isPsgUser;
```

Thus NPP MSP users use the non-flexible exception form: NPI, SSN, First Name, Last Name; no Reason, State, or License fields. Recruitment/PSG get Reason, Last Name, SSN, First Name, DOB, and Email.

On `/Npp`, the page passes `ForceNpiSearchMode` to the form, which prevents initial auto-switching:

```csharp
if (!_isRecruitmentUser && !_isPsgUser && !ForceNpiSearchMode)
    SwitchToExceptionSearch();
```

But the shared “No NPI available?” link is still rendered, and `SwitchToExceptionSearch` has no NPP-specific restriction. The page passes `IsNppRequest` to the table, not to `PractitionerSearchForm`. So the route begins in NPI mode but does not currently isolate or specialize exception search.

**F. Search parameter fields**

`PractitionerSearchParameters.cs` has FirstName, LastName, SSN, NPI, EmailAddress, DOB, and other existing search fields. **No State or LicenseNumber properties.**

**G. Recruitment Last-name validation**

Recruitment exception search requires at least one additional criterion with Last Name:

```csharp
if (!hasAdditionalCriterion)
{
    throw new ArgumentException(
        "At least one additional search criteria is required along with Last Name");
}
```

The UI also enables flexible-user exception search only when Last Name, Reason, and at least one additional criterion are present. Recruitment’s exception search is therefore not reusable for the requested NPP “Last Name only” case.

**H. Audit pattern**

CredentialingAuditLogger.GetAffVerifyPractitionerSearchAuditLog constructs an `AuditLog` containing action, current user, and entered criteria. Cactus API’s `PractitionerRepository.SearchPractitionersAsync` then calls:

```csharp
await _serviceBusService.QueueAuditLogEntry(
    _auditLogger.GetAffVerifyPractitionerSearchAuditLog(...));
```

`ServiceBusService.QueueAuditLogEntry` serializes to the `audit-log` queue; Background’s `AuditLogFunctions.CreateAuditLogEntry` consumes and persists it. AffVerify is the existing example, but the product explicitly says not to reuse its action.

**I. New audit action**

The pipeline can carry a new action: `AuditAction` is an enum stored in the `AuditLog` payload and the audit consumer persists it generically. However, audit retention is action-specific: `CredentialingAuditLogRepository.PurgeAuditLogsAsync` keeps only AffVerify actions for five years and deletes other actions after 180 days. A new NPP action can reuse the transport/persistence pipeline, but its retention duration needs an explicit decision. Do not send it under an AffVerify action.

**J. Cancel on `/Npp`**

For non-flexible users, Cancel does this:

```csharp
await JsRuntime.InvokeVoidAsync("history.back");
```

It does not clear the exception criteria and return the same form to NPI mode. Recruitment/PSG instead clear exception fields and switch modes.

**K. License API reverse lookup**

No existing reverse lookup by State + license number was found. `PractitionerLicenseController`’s state-license endpoint is keyed by practitioner key; its other license search methods accept practitioner/item criteria, not state plus license number. The existing `GetExistingStateLicense` also requires provider key.

**L. STOP risks / host boundary**

`CrudLicensesAndCertificationsOperation` belongs to Packet.Processor and receives its `CactusDbContext` from the processor’s `CactusUpdater`. It is not a service callable from the UI.

The UI calls Cactus API’s `PractitionerController.SearchExistingPractitionersAsync`. Cactus API has a `PractitionerRepository` configured with `_cactusDb`; a new reverse lookup belongs in that API repository/endpoint, not by calling a Processor operation from the UI. PAF API’s `Startup` configures PAF, User, and Packet DB settings, but not `CactusDb`.
