**A. Call Chain**

- `CactusUpdater.InternalUpdateCactusFromPafAsync` routes an NPP PAF through the new-practitioner or existing-practitioner path according to `paf.Practitioner.IsNew`.
- In the existing-practitioner NPP branch, the updater calls `CrudPractitionerLicensesOperation` with `IsAddPractitionerToFacility = false`, then creates the standard CVI records.
- `SavePractitionerLicensesAsync` handles Add Practitioner defaults and Recruitment state licenses on their respective paths. For a completed NPP task, it calls `CreateOrAttachNppSanctionCheckAsync` after those sections. There is no NPP state-license create/update branch in that operation.

Evidence: `CactusUpdater.cs`, `CrudPractitionerLicensesOperation.cs`

**B. Duplicate Check**

The Recruitment state-license path checks provider plus license type, state, and number:

> `AND LICENSE_RTK = @LicenseTypeRtk`  
> `AND STATE = @State`  
> `AND LICENSENUMBER = @LicenseNumber`

This matches the requested duplicate fields, scoped to the practitioner. It does not filter by `ACTIVE`, so an inactive matching license is still considered a duplicate there.

**C. Create Defaults**

The existing Recruitment path uses the literal `"NPDBSTATEx"` and inserts with state and normalized number. The shared insert helper sets `Persistentverifications = true`, `Npdbprimarylicense = false`, `LicensurefieldRtk = CommonCactusRtks.NoneRtk`, and `Active = true`. Its signature does not accept effective/award date, expiration date, licensure field, or enrollment-status RTK.

That does **not** match the ticket defaults: the ticket says `NPDSTATEx` (without the `B`), `NPDBPrimaryLicense=T`, and specifies dates, licensure field, and `LICMONENROLLMENTSTATUS_RTK`. No named State License RTK constant was found in the inspected operation constants; the existing Recruitment code uses the literal `NPDBSTATEx`. **Ashley/ADO confirmation is needed** for the ticket’s `NPDSTATEx` versus repository `NPDBSTATEx`, and for `LICMONENROLLMENTSTATUS_RTK` and its requested value. I will not infer or substitute those values.

**D. Active Preserve / Inactive**

There is no NPP state-license behavior to quote for 132644 or 132645. Today, the NPP operation does not read or update the selected/new state-license fields. Recruitment behaves differently: a matching license is set `Active = true` and passed to `UpdateLicenseAsync`; reusing that behavior for NPP could violate the “active practitioner elsewhere: no updates” requirement. NPP needs its own rules for preserving existing records and handling an inactive practitioner.

**E. Image Path / `D2B50K69Z8`**

`NppTask` contains `LicensePsvAttachment` and `LicensePsvAttachmentUrl`, but the NPP processor does not use them. The existing NPP sanction path demonstrates the image pattern: `CrudImagesOperation` creates a Provider License image, then the attachment is queued for conversion. It uses image type `S3PK02WN8H`, a `_Sanctions_` description, and notes `Uploaded via auto PAF for ADD NPP to Facility`. No State License image path or `D2B50K69Z8` use was found in the processor/tests inspected.

**F. `NppTask` License Sources**

The model defines `SelectedStateLicenseKey`, `NewLicenseState`, `NewLicenseEffectiveDate`, `NewLicenseNumber`, `NewLicenseStatusRtk`, `NewLicenseExpirationDate`, and `NewLicenseFieldOfLicensure`. It also defines `LicensePsvAttachment` and `LicensePsvAttachmentUrl`, separate from `SanctionsPsvAttachment` and `NpiPsvAttachment`. These are currently model/validation properties, not inputs consumed by `CrudPractitionerLicensesOperation`.

Evidence: `NppTask.cs`

**G. NPP Gap**

**Yes.** NPP has no State License create/duplicate/preserve/inactive handling and no State License PSV image attachment path. The sanction-license path is separate and currently executes after the other license sections; it should remain intact.
