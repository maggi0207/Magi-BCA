**NPP-only differences**
The working OffCycle upload uses `FormType.Mss19LoaForm`; NPP uses `FormType.Other`. That is the only apparent upload-metadata difference in the component markup. The controller has no FormType whitelist: it checks file extension, uploads/scans the blob, and copies the supplied FormType into the attachment record.

OffCycle passes `StateContainer.PafState.OffCyclePsvTask.TaskId`. NPP passes `StateContainer.PafState.NppTask.TaskId`. `BasePractitionerActionFormTask.TaskId` defaults to a new GUID, and NPP assigns its task to PafState when the form initializes. That makes the task available in client state before the upload; it does not demonstrate that the NPP task has already been saved back to the PAF server.

PafFile itself obtains `PractitionerActionFormId` from `StateContainer.PafState.FormId` and does not pass `FacilityKey`. The upload API accepts and copies `FacilityKey`, but the other PafFile hosts also omit it. In the code inspected, FormType, TaskId, and FacilityKey are not individually rejected by a whitelist or validation branch.

**Conclusion**
The observed NPP-specific candidate is `FormType.Other` versus OffCycle’s task-specific value. Repository code does not show the API rejecting `Other`, so it does not establish that as the live failure cause. TaskId is present in NPP client state; whether it is already server-persisted before upload is not established by this code path. No enum, API contract, Cactus, or other change was made.
