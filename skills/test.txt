# Fix EmployerDetails Update and Delete APIs – Minimal Payload and Existing WorkEdge Pattern

## Current Situation

In the WorkEdge Employer service:

- Insert EmployerDetails is working successfully.
- Update EmployerDetails is failing.
- Delete EmployerDetails is failing.
- Swagger currently generates request payloads containing every EmployerDetails field, including unnecessary placeholder values.

Existing endpoints:

```text
POST /Employer/EmployerDetails/InsertEmployerDetails

POST /Employer/EmployerDetails/UpdateEmployerDetails

POST /Employer/EmployerDetails/DeleteEmployerDetails
```

The database table is:

```text
customer.employer_details
```

Primary key:

```text
employer_id
```

## Objective

Fix the Update and Delete EmployerDetails operations.

The implementation must:

1. Accept only the required request fields.
2. Follow the existing WorkEdge and FACTS framework patterns.
3. Use the existing Controller and BusinessLogic structure.
4. Preserve the working Insert functionality.
5. Correctly update and delete database records.

## Step 1 – Analyse Existing Implementation

Before modifying code, inspect:

- Employer service controller
- EmployerDetails request DTOs
- EmployerDetails BusinessLogic
- DbContext and entity mapping
- Existing Insert implementation
- Existing Update/Delete implementations from similar WorkEdge services
- Swagger request and response configuration

Identify the exact reason why Update and Delete are failing.

Do not assume the issue is caused by the HTTP method.

## Step 2 – Update Request Payload

Inspect the existing Update request model.

Ensure Swagger does not require unnecessary fields when the operation only needs:

- employerId
- Fields being updated

For example, if the existing contract supports updating only the employer name:

```json
{
  "employerId": 468,
  "name": "Updated Employer Name"
}
```

Use the actual DTO and validation rules as the source of truth.

Do not invent new fields or remove genuinely required fields.

## Step 3 – Fix Update BusinessLogic

Follow the existing WorkEdge BusinessLogic pattern.

Requirements:

- Retrieve the existing record using employerId.
- Return the standard not-found response if the record does not exist.
- Update only the permitted fields.
- Preserve create_date and create_user.
- Update modification_date and modification_user using existing audit conventions.
- Maintain modification_number according to the existing pattern.
- Save changes using the existing DbContext.
- Return the standard response model.

Avoid overwriting existing values with default or placeholder values.

## Step 4 – Fix Delete Request

Inspect the existing Delete DTO and endpoint.

If deletion requires only the primary key, the payload should be:

```json
{
  "employerId": 468
}
```

Requirements:

- Validate employerId.
- Retrieve the existing record if required by the existing pattern.
- Follow the project's physical-delete or soft-delete convention.
- Respect existing business rules and relationships.
- Handle missing records correctly.
- Return the standard response model.

## Step 5 – Verify HTTP Methods

Inspect the existing WorkEdge CRUD implementation and FACTS framework conventions.

Determine whether the project uses:

- POST for all service operations
- PUT for complete updates
- PATCH for partial updates
- DELETE for deletion

Do not change the HTTP method simply because Update or Delete is failing.

If the current framework convention uses POST, retain the existing endpoint contract.

If the project requires REST-standard methods, update the controller attributes, route, Swagger definition, and client proxy consistently.

## Step 6 – Swagger Validation

After implementation:

- Verify the Update request shows only required fields.
- Verify the Delete request shows only required fields.
- Confirm the correct request content type.
- Confirm all required FACTS context headers are present.
- Execute Insert, Update, and Delete.
- Confirm that the database record is updated or deleted correctly.
- Confirm Insert remains unaffected.

## Final Report

Provide:

- Root cause of Update failure
- Root cause of Delete failure
- Required payload for each operation
- HTTP methods retained or changed, with reason
- Controller and BusinessLogic files modified
- Build and test results

Make the smallest possible change and follow the existing WorkEdge pattern exactly.
